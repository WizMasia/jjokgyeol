# 쪽결의 기기 글꼴 선택과 문서 내장

## 선택한 방식

사용자는 PDF와 편집용 `.jjok`에 글꼴을 자동 포함하는 방식을 선택했다. PDF에만 내장하고 편집 문서에는 이름만 남기는 방법도 검토했다. 이름만으로는 다른 컴퓨터에서 같은 버전의 글꼴로 이어서 조판하기 어렵다. 편집용 문서에 원본을 담을 권한이 확인되면 글꼴과 배포에 필요한 고지를 함께 보관한다.

목표는 사용자가 평소처럼 글꼴을 고르고 저장하는 것이다. 교정 PDF 포함 여부는 지금처럼 사용자가 선택한다. 교정 PDF를 빼고 저장해도 편집에 필요한 글꼴은 같은 기준으로 포함한다. 다음 절의 형식 범위와 권한 확인 방법은 구현을 위한 제안이다.

## 글꼴 선택과 라이선스 확인 도구

- macOS·Windows·Linux 네이티브 앱은 각 운영체제가 앱에 제공하는 설치 글꼴을 보여준다. 웹은 사용자가 ‘기기 글꼴’ 버튼을 누를 때 지원되는 브라우저 API로 접근을 요청한다. 접근이 거부되거나 API가 없는 환경에서도 기본 글꼴과 로컬 파일 선택을 사용할 수 있다. 목록과 선택하지 않은 글꼴 파일은 기기에 남는다. [Local Font Access API](https://developer.chrome.com/docs/capabilities/web-apis/local-fonts)
- 첫 버전은 정적 TrueType·OpenType 단일 글꼴 파일을 조판한다. 컬렉션, 가변 글꼴 등 현재 경로에서 동일하게 재현할 수 없는 형식은 선택 목록에서 이유를 보여주고 다른 지원 파일을 고를 수 있게 한다. 보통·굵게 파일을 개별 검사하고 연결한다. 특정 굵기가 없으면 해당 굵기의 쪽결 기본 글꼴을 쓰고 그 사실을 표시한다. 실제 파일이 같은 항목은 한 번만 읽고 저장한다.
- 글꼴 선택 옆의 ‘라이선스 확인’은 현재 선택 또는 직접 연 파일에 대해 이름·버전·굵기, 저작권자 표기, 약관 설명과 원본 링크, 내장 제한, 판단 근거를 표시한다. ‘PDF 내장’과 ‘편집 문서에 원본 포함’ 각각에 **허용 / 제한 / 근거 부족**을 표시한다. 로컬 검사는 오프라인에서도 동작하고 약관 링크는 사용자가 열 때만 접속한다. [OpenType 이름과 라이선스 필드](https://learn.microsoft.com/en-us/typography/opentype/spec/name)
- 파일의 SHA-256으로 실제 글꼴을 식별한다. 현재 나눔 글꼴 네 파일과 고지는 `runtime.lock`의 해시를 재사용한다. 다른 파일은 OpenType의 `OS/2.fsType`을 버전에 맞게 해석하고 파일에 표시된 약관과 대조한다. PDF 내장을 허용하는 명시적 표시 또는 확인된 약관을 근거로 사용한다. 별도 약관이 명시되어 있으나 그 적용 범위를 해석하지 못하거나 두 근거가 충돌하면 ‘근거 부족’으로 표시하고 대체한다. 기본값 0만 있고 라이선스 근거가 없는 파일도 같은 처리를 한다. 사용한 글자만 내장하는 것이 금지된 경우 전체 내장이 허용되고 실제 조판기가 이를 보장하는 경우에만 전체를 넣는다. 비트맵만 허용하는 파일은 현재 윤곽선 조판 경로에서 대체한다. [OpenType 내장 권한](https://learn.microsoft.com/en-us/typography/opentype/spec/os2#fstype)
- 원본 포함은 더 구체적인 근거가 필요하다. 첫 버전은 해시로 확인된 배포본과 고지, 또는 글꼴 자체의 라이선스 문구가 명시적으로 SIL OFL 1.1을 지정하고 해당 파일의 저작권 표기와 OFL 전문을 함께 보존할 수 있는 경우를 자동 지원한다. 그 밖의 약관은 검사 결과를 보여주고, 개별 배포본과 권한을 검토해 해시 기반 정책에 등록할 수 있다. 글꼴 이름, 링크, 출처가 확인되지 않은 별첨이나 문서 안의 ‘허용’ 표시만으로 원본을 포함하지 않는다. 정보가 충돌하면 해당 용도는 보류한다. [SIL OFL 1.1 전문](https://openfontlicense.org/open-font-license-official-text/)

## 조판과 웹 전송

본문·제목·단계별 제목·머리말과 꼬리말·텍스트 역할 등 기존에 글꼴을 지정하는 모든 위치가 같은 문서 글꼴 목록을 사용한다. 기존 내장 글꼴 키를 유지하고, 새 글꼴 참조는 보통·굵게 파일 해시를 식별할 수 있게 한다. 양식 JSON에는 참조만 저장한다. 양식을 단독으로 다시 열면 정확히 일치하는 파일을 다시 연결할 수 있고, 누락된 참조도 다음 저장까지 보존한다.

미리보기, 규칙·모델 조판, 최종 PDF가 동일한 글꼴 해석 결과를 받는다. 미리보기·인쇄만 허용하는 글꼴은 읽기 전용 교정본에 한해 내장한다. 다운로드할 PDF가 그 조건을 보장하지 못하면 대체한다. PDF에 내장된 글꼴을 추출해 편집 자원으로 재사용하는 경로는 두지 않는다. 정책상 대체가 필요하면 요청 글꼴과 실제 적용한 글꼴 및 이유를 표시한다. 기존 글자별 대체와 PDF 텍스트 추출을 유지한다. 디시전 제공자에게 글꼴 파일을 전송하지 않는다. [OpenType의 미리보기·인쇄 조건](https://learn.microsoft.com/en-us/typography/opentype/spec/os2#fstype)

네이티브는 선택된 파일을 로컬 작업 공간에서 사용한다. 웹은 브라우저에서 검사하고 실제 PDF는 기존 Docker 조판기에서 만든다. 조판기에 이미 있는 동일 해시 파일을 우선 사용한다. 파일을 보내야 할 때는 목적지와 전송 이유를 표시하고 해당 세션에 대해 한 번 동의를 받는다. 원격 서버 전송은 서버 사용 및 복사가 허용된 배포본에 한한다. 허용된 재배포·사용 범위가 이를 충족하는 OFL 파일도 여기에 해당한다. 로컬 전용 사용 조건은 네이티브 또는 루프백의 로컬 조판에서 처리한다. 위치를 확정하기 어려운 조판기는 원격으로 취급한다. 전송 거절·권한 부족 시에는 기본 글꼴로 계속한다. 검사만으로 업로드가 발생하지 않는다.

전송 수신부와 네이티브 워커에서 크기·형식·해시·테이블 범위를 확인하고 세션 또는 작업 전용 경로에서만 파일을 연다. 사용자 파일명과 글꼴 내부 이름을 TeX 경로나 명령으로 해석하지 않는다. 파일 수, 파일당 바이트, 작업 총량, 압축 해제 총량은 공통 운영 설정에서 관리한다. 현재 시험판의 나눔 네 파일은 총 17,357,120바이트이고 가장 작은 파일도 기존 원고·양식 요청 한도인 1 MiB를 넘는다. 글꼴 바이너리 전송과 ZIP 글꼴 항목에는 전용 한도를 적용하고, 원고·양식에는 기존 한도를 적용한다. 문서 총한도는 교정 PDF와 글꼴을 함께 담는 경우를 검증한다. 내장 글꼴 파일은 사용자가 OS에 설치할 필요가 없다.

## 저장과 다시 열기

1. 새 저장 형식은 `.jjok` 버전 2다. 기존 원고·정수 양식·선택적 PDF 구조에 글꼴 참조와 원본·고지 목록을 추가한다. 각 글꼴에는 요청 이름·버전·굵기·파일 해시 및 포함 여부를 기록한다. 원본과 고지는 해시 기반 이름으로 한 번씩 저장하고 참조로 연결한다. 웹과 네이티브가 같은 형식을 쓴다.
2. 현재 양식이 참조하는 글꼴과 실제 편집·조판에 필요한 기본 대체 글꼴을 대상으로 삼는다. 기본 나눔 글꼴도 같은 자동 포함 정책을 적용한다. 편집 과정에서 새로 쓸 수 있는 연결된 굵기도 포함한다. 글꼴 선택 목록 전체를 묶지 않는다. 원본 포함이 제한된 글꼴은 참조를 유지한다. 별도 기기에서 같은 파일을 연결하면 재조판할 때 원래 선택을 복원한다.
3. 열 때에는 기존 버전 1과 새 버전 2를 모두 읽는다. 버전 2에서는 목록에 선언한 항목만 받아들이고 파일·고지의 해시, 중복, 경로, 개수, 압축 해제 크기를 검사한다. 구조가 깨진 문서는 현재 편집 내용을 교체하기 전에 오류를 표시한다. 구조가 유효하지만 권한을 확인할 수 없는 글꼴은 사용·재포장 여부를 다시 판단하고 필요하면 대체한다. 저장된 허용 판정은 재검사를 생략할 근거가 아니다.
4. 열 때는 문서에 담긴 글꼴, 현재 기기에서 접근을 허용한 같은 해시 파일, 쪽결 기본 대체 글꼴 순으로 해석한다. 대체해도 양식의 원래 참조를 보존한다. 기존 교정 PDF는 즉시 열 수 있다. 새 조판에서 다른 글꼴을 써야 한다면 기존 PDF 상태를 이전 교정본으로 표시하고, 사용자가 다시 조판할 때 새 지면을 반영한다.
5. 검사·선택·미리보기·저장은 해당 원고와 양식 버전에 묶는다. 파일 교체·취소 후 늦은 결과가 새 문서에 적용되지 않도록 한다. 한도 초과·저장 실패는 편집 내용과 기존 파일을 보존하고 원인을 안내한다. 웹 다운로드와 네이티브 저장 완료의 기존 확인 방식도 따른다.

## 인수 조건

- 설치 글꼴 목록, 접근 거절, 목록 API가 없는 웹, 오프라인 네이티브, 파일 직접 선택에서 같은 파일의 검사 결과가 일치한다. 목록 조회와 라이선스 확인만으로 전송이 발생하지 않는다.
- 나눔 네 파일, 추가 OFL 파일, PDF만 허용된 파일, 부분 내장 금지, 비트맵 한정, 표시 누락·충돌·손상을 검사한다. 권한마다 PDF의 실제 글꼴 스트림과 `.jjok`의 원본·고지를 각각 확인한다. 부분 내장 금지 파일은 실제 전체 내장을 입증하거나 대체해야 한다.
- 허용된 외부 글꼴이 설치되지 않은 다른 환경에서 웹↔네이티브로 문서를 교환하고 재조판한다. 같은 엔진에서 규칙 조판과 고정한 모델 결정을 각각 사용해 쪽 수, 줄 끝 어절, 글자 좌표, 여백 번호, 한글 텍스트 추출을 비교한다.
- 기존 버전 1 읽기, PDF 포함 켜기·끄기, 누락 글꼴 재연결, 단독 양식 왕복, 이전 교정본 보존, 느린 검사·저장 중 원고 전환, 변조·크기 초과 파일 거절을 확인한다.

파일 전송 방식, 운영 한도의 수치, 운영체제별 열거 API와 구체적인 UI 배치는 구현자가 기존 웹·네이티브 호출 경로와 실측을 바탕으로 정한다. 로컬 웹과 Mac 시험판에서 실제 저장·열기·조판을 검증한다. Windows·Linux의 설치 목록과 직접 선택은 플랫폼별 테스트 대상으로 남기고, 해당 환경에서 실행한 결과를 별도로 기록한다.
