# 출판 설정창

원고와 지면이 있는 기본 창의 도구 막대에 설정 버튼을 둔다. 네이티브 앱은 독립 창 한 개를 열고 재호출 시 작성 중인 창으로 초점을 옮긴다. 웹에서는 같은 입력 UI를 모달 대화상자로 연다. 파일 형식과 기본값은 기존 Style 모듈을 따른다.

- [x] 네이티브에서는 메인 창이 편집 양식의 스냅샷을 전달한다. 설정창은 조판·견본 원고를 시작하지 않는다. 적용은 검증한 양식을 메인 창에 전달하고, 취소는 메인 창에 쓰기 전에 닫는다. 원고 상태와 PDF는 설정창에 넘기지 않는다. 원래 창이 닫히면 설정창도 정리한다.
- [x] 웹의 출판 양식, 양식 파일, AI·참고 문서·머리글 도구는 설정 안에서 계속 사용할 수 있다. 열기·닫기와 초점 복귀를 시험한다.
- [x] 기존 양식의 mm·pt, 자간, 양면 여백, 저장과 열기를 정상 진입점에서 검사한다. 창 중복, 변경 적용, 취소, 저장하지 않은 원고 보존을 확인하고 Mac 앱에서 두 창과 PDF를 직접 확인한다.

## 실행 검증

- macOS 개발 앱에서 본문을 11pt에서 13pt로 바꿨다. 설정 버튼을 다시 눌러도 동일한 창과 입력값이 유지됐고, 적용 후 갱신한 PDF는 13pt였다. 14pt로 바꾼 뒤 적용 전에 닫고 다시 열었을 때는 13pt였다. 별도 16pt 양식 JSON도 시스템 파일 선택기로 열어 적용하고 새 PDF를 확인했다. 0pt를 입력해 적용했을 때는 범위 오류가 표시됐고 Escape로 취소할 수 있었다.
- macOS에서 백그라운드 원고 창의 설정 버튼을 접근성 API로 눌렀을 때 새 창의 내용이 비는 현상을 재현했다. 새 창 생성 직후에도 기존 창과 같은 방법으로 초점을 지정한 뒤, 네 번 연속 한 번의 클릭으로 0.71~1.31초 안에 설정 입력란을 확인했다.
- Windows x64에서 원고 창과 설정창의 핸들이 달랐다. 설정창에 닫기 메시지를 보낸 뒤 원고 창이 남았다. Ubuntu 24.04에서는 접근성 API로 원고 창의 설정 버튼과 설정창의 닫기 버튼을 눌렀다. [Windows 실행 기록](https://github.com/WizMasia/jjokgyeol/actions/runs/44744324666) · [Linux 실행 기록](https://github.com/WizMasia/jjokgyeol/actions/runs/44744324648)
- 웹은 320px, 390px, 1280px 너비에서 대화상자 열기, 세부 항목 펼치기, Escape로 닫기와 설정 버튼 초점 복귀를 확인했다. 실제 모델을 연결한 편집기에서도 같은 조판 요청으로 받은 두 PDF를 선택하고 각각 다운로드했다.
- 보존한 웹판과 변경판에 11쪽·12쪽 원고를 각각 고정 여백과 맞쪽 여백으로 조판했다. 네 조합 모두 규칙 PDF의 쪽 크기와 모든 글리프 좌표가 일치했다. 오래된 기준 PDF와의 비교에서는 긴 각주를 단 본문 한 줄의 글리프가 약 3.29 PDF pt 달라지는 현상이 있다. 같은 브라우저 조판 요청에서 설정창 분리 이전 웹판도 이 차이를 보였다. 과거 지면을 기준으로 한 11개 검사에서 두 버전의 실패 목록이 같았다.
- 현재 소스로 오프라인 웹 테스트 1,134건을 네 그룹으로 나누어 실행했다. 1,072건이 통과했고 외부 연결 등 별도 환경을 요구하는 62건이 건너뛰어졌다. 데스크톱 프런트엔드 검사 7건과 Rust GUI 단위 검사 7건도 통과했다.
